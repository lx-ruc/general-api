## 修复的缺陷（本轮验收发现并修复，均附回归测试）

| # | 严重度 | 缺陷 | 修复 |
|---|--------|------|------|
| 1 | 高 | JWT 中间件不回库校验：禁用/删除账号、停用组织的存量 token 在 12h TTL 内仍可操作管理台 | `JWTAuth` 每请求回库校验 status/role/org 状态（`internal/middleware/auth.go` + 5 个单测） |
| 2 | 高 | 上游 401/403 直接跳下一**渠道**：单渠道多 Key 池撞坏 Key 首笔即 502，违反需求 3.6「自动切备用 Key」 | 改为同渠道换下一把 Key，坏 Key 自动置 status=0（`internal/gateway/handler.go`） |
| 3 | 高 | 删除客户/子账号不级联：孤儿账号仍可登录、API key 残留可继续调用 | DeleteOrg/DeleteMember 事务级联删除用户与 api_keys（`internal/api/{platform,org}/handler.go`） |
| 4 | 中 | 欠费停服（status=2）拦登录：客户无法进管理台查账单/申请充值，与 README 承诺矛盾 | 登录与 JWT 只拦手动停用（0）；欠费停服仅拦数据面（`internal/api/auth_handler.go`） |

## 已知边界（非缺陷，记录备查）

1. **缓存命中不计量**：`cache_ttl > 0` 时相同非流式请求直接回缓存，`cost=0`、`cache_hit=1` 照常写 usage_logs —— 这是精确缓存的设计语义（省上游 TPM），计费审计以 usage_logs 为准。验收脚本对每笔请求注入唯一 nonce 以击穿缓存验证真实计费路径。
2. **欠费翻转条件**：`quota_used >= quota_limit` 在 Settle 事务内判定，单笔超扣幅度封顶在该笔成本内（advisory 预检 + 无条件结算的既定设计）。
3. **渠道 PUT 为全量对象语义**：`channelReq` 对 name/base_url/models 均 required，部分字段更新会 400（前端表单本就提交全量）。
4. **`deepseek-chat` 上游状态**：官方 2026-07-24 起标记弃用（别名到 deepseek-v4-flash），当前仍可用；换代方案见《模型换代调研报告》。
