# 高并发 / 高可用设计记录

> 背景：对外卖服务，几百路并发 API 调用（≈20-100 RPS 稳态），首要目标是"不停"。

## 结论

- **吞吐完全不是瓶颈**：单机完整链路（鉴权→授权→预检→路由→上游转发→计费结算）实测 2161 RPS（PG 模式，本地 mock 上游，40 并发），是预期负载的 20 倍以上
- **"停"才是敌人**：采用 PG + 双网关 + Caddy 轮询健康检查
- **上游限流才是新瓶颈**：网关吞吐远超厂商配额后，加入了 `internal/coord` 协调器 —— 渠道 Key 池、429 冷却重试、并发闸门排队削峰、精确缓存；多实例时引入 Redis 全局共享（不配则进程内存，per-node 降级）

## 压测数据（2026-09-06，本机，mock 上游）

| 场景 | 结果 |
|---|---|
| `GET /v1/models`（鉴权联表+授权查询，**SQLite**，并发 20×3000，Python 实测） | **3,587 RPS**，串行 avg 0.86ms |
| `GET /v1/models`（同路径，**PG**，hey 并发 50） | **7,832 RPS**，avg 6.2ms |
| `POST /v1/chat/completions` 完整链路（**PG**，40 并发×50 key，Python 实测） | **2,161 RPS**；放行的 200 请求 p50 13.7ms / p99 90ms；429 为 per-key 限流（60RPM+burst10）精准拦截，0 5xx |

方法：Python 并发客户端为主（hey 在 macOS 超短测试下速率统计失真，仅取其自洽数据点）；mock 上游排除厂商 RT 干扰。

结论：SQLite 单机读路径 3.5k RPS、PG 7.8k、完整计费链路 2.1k —— 对目标负载（20-100 RPS）均有 20 倍以上余量；瓶颈不在网关，在厂商上游。

## 架构

```
客户 ──▶ Caddy (TLS, round_robin + /healthz 健康检查, SSE flush -1)
          ├── gateway ×N（无状态：验证码/限流之外的 state 全在 DB + Redis）
          ├── Redis（协调器：Key 冷却 / 渠道并发闸门 / 精确缓存；可选）
          └── PostgreSQL（结算事务/行锁，多写者安全；WAL 备份）
```

### 高并发协调器（internal/coord）

| 能力 | 机制 | 多实例 |
|---|---|---|
| 渠道 Key 池 | `channel_keys` 表多把 key 加权调度，429 冷却过滤，401/403 自动禁用（管理台可恢复） | DB 共享 ✓ |
| 429 感知重试 | `SET NX EX` 冷却（Retry-After 优先）；同渠道换 key，渠道耗尽回 429 `upstream_busy` | Redis 全局 / mem per-node |
| 并发闸门（排队削峰） | ZSET 租约 + Lua 原子占坑 + 心跳续租（进程崩溃最迟 lease=45s 自动回收）；满员 50→200ms 退避轮询 `queue_wait_timeout` | Redis 全局 / mem per-node |
| 精确缓存 | 白名单字段固定顺序 SHA-256；仅非流式 2xx ≤1MB；命中 cost=0、`X-Tg-Cache: hit` | Redis 共享 / mem per-node |

- Redis 故障 **fail-open**：不冷却/放行/缓存 miss，限频告警 + `tg_coord_redis_errors_total` 计数，绝不拖死数据面
- `redis.addr` 留空 = 纯内存模式（单机零依赖）；此时闸门/冷却/缓存为 per-node，多实例实际并发 ≈ max × 节点数

多实例下仍为本地的状态与取舍：
- **限流**：per-node 内存令牌桶 → 单 key 实际上限 ≈ 配置 × 节点数。几百客户场景误差可接受；需要精确全局时上 Redis
- **渠道熔断计数**：per-node（触发更快，无害）
- **验证码**：已入库（verification_codes 表），多实例共享 ✓

## 关键实现点

- `database.driver: sqlite | postgres` 双模式；schema.sql 以 SQLite 方言书写，PG 执行前模板替换
  （`AUTOINCREMENT → GENERATED BY DEFAULT AS IDENTITY`、`INTEGER → BIGINT`、跳过 PRAGMA）
- 迁移工具 `-migrate-from-sqlite`：逐表搬运 + 行数核对 + identity 序列 setval 及回读校验
  （防御 PG 的 `ON CONFLICT DO NOTHING` 仍消耗序列的经典坑）
- 渠道熔断：连续失败 N 次（默认 5）自动 `status=0` 并写备注；成功一次清零
- `/metrics`：零依赖手写 Prometheus 文本格式（请求量/延迟直方/活跃 SSE 流/上游错误/结算失败/熔断计数/
  上游 429/Key 冷却/Key 禁用/排队时长直方/排队超时/缓存命中/协调器 Redis 故障）
- 滚动发布：LB 摘流 → 换一台 → 健康检查 → 换另一台（见 deploy/docker-compose.yml）

## 遗留（真到了再做）

- Redis 精确全局限流（per-key 令牌桶全局化；当前每请求直查 PG，7.8k RPS 下无需缓存）
- PG 流复制热备或云 RDS
- 结算批量聚合（RPS 上千且 PG 写成为瓶颈时）
